# P3 — scope for the authenticated API and application shell

**Status:** proposal, design-only. Nothing here authorises code.
**Author:** maintainer · **Date:** 2026-07-29 · **Master at time of writing:** `2717eb6`

P2 is accepted. This proposes how P3 is broken up, and — more usefully — names the
decisions that have to be made before any of it starts.

Checkpoints are referred to **by name, never by migration number**. Every spec that
pinned a number has been overtaken by the time anyone implemented it; that is now a
standing rule in `CONTRIBUTING.md`.

---

## 1. Where P3 actually is — measured, not estimated

| | Count |
|---|---:|
| Domain functions across `meridian/*.py` | **56** |
| HTTP endpoints that exist | **2** (`/health`, `/health/engine`) |
| Frontend routes | **11** |
| Frontend mock APIs | **10** |
| Lines of authentication | **0** |

`grep` for `jwt`, `passlib`, `bcrypt`, `set_cookie` or an auth dependency across
`meridian/` returns nothing. There is no user credential anywhere: `principal` carries
name, email, role and clearance, but nothing to authenticate *with*.

So P3 is not "wire up the API". It is: build an authentication system that does not
exist, put it in front of 56 functions that assume a trusted caller, and replace ten
mock modules — without weakening the tenancy P1 and P2 spent five releases hardening.

---

## 2. The security question that dominates P3

**Read this before designing any endpoint.**

Every domain function takes `workspace_id` as an ordinary argument:

```python
def list_resolutions(*, workspace_id: str = DEFAULT_WORKSPACE_ID, ...)
```

It reaches Postgres through `store.pg(workspace_id)`, which sets `app.workspace_id`
— the GUC every RLS policy reads. That design is correct today because the only
callers are the CLI and tests, both trusted.

**The moment an HTTP request can influence that value, RLS is bypassable by anyone
who can send a request.** `GET /api/resolutions?workspace_id=<someone-else's>` would
be honoured by the database, because the database was told to trust the GUC.

This is limitation #1 in the P2 acceptance record — *"`app.workspace_id` is an
ordinary GUC, so RLS guards application bugs, not a compromised runtime role"* — and
P3 is where it stops being theoretical.

**The rule this proposal recommends adopting as non-negotiable:**

> `workspace_id` and `clearance` are derived from the authenticated session on the
> server. They never appear in a request path, query string, body, or header. An
> endpoint that accepts either as input is a defect, and there should be a test that
> fails if one ever does.

`identity.resolve_principal()` already does the right thing — it JOINs
`principal → membership` and fails closed when there is no active membership. P3's
job is to make that the *only* way a request acquires a workspace, not to invent a
new path.

## 3. Four mock modules have no backend to wire to

The `lib/*.ts` modules were written to mirror Python contracts field-for-field so the
swap would be mechanical. For six of them it is. **Four have no counterpart at all:**

| Mock | Backend | What P3 must decide |
|---|---|---|
| `board-members.ts` | `meridian/board_members.py` | — mechanical |
| `decisions.ts` | `meridian/decisions.py` | — mechanical |
| `meetings.ts` | `meridian/meetings.py` | — mechanical |
| `minutes.ts` | `meridian/minutes.py` | — mechanical |
| `packs.ts` | `meridian/packs.py` | — mechanical |
| `resolutions.ts` | `meridian/resolutions.py` | — mechanical |
| `documents.ts` | **none** | `document` is in the frozen core schema with no `meridian/` module. Read it through `callosum.store`, or add a product-side module? |
| `graph.ts` | **none** | Generated from `GOLD_GROUPS` by a script. The real source is Neo4j via `callosum.retrieve`. Is `/memory` a live view or a demo artifact? |
| `assistant.ts` | **none** | Maps to `callosum.retrieve.ask()` — a frozen-core call with an LLM behind it. Latency, cost and streaming are all unanswered. |
| `insights.ts` | **none** | Dashboard metrics. **No source exists.** This is the module whose fabricated numbers were removed twice. |

`insights.ts` is the one to watch. It has already been the site of two data-honesty
failures, and it is the only mock with nothing real behind it. The honest options are
to derive every tile from a real query or to delete the tiles that cannot be — not to
wire it to something approximate.

## 4. Proposed checkpoints

Same shape that worked for P2: one thing per checkpoint, each with its own tests, and
nothing starts until the previous one passes.

**CP-A — Identity and session.** The auth mechanism, a session that carries
`principal_id`, and `workspace_id` + `clearance` derived from it via
`resolve_principal()`. No domain endpoints. Exit: a request cannot influence which
workspace it reads, and a test proves it.

**CP-B — One vertical slice, read-only.** A single aggregate (recommend `resolutions`
— it is the newest contract and the frontend surface already exists) exposed end to
end: endpoint, session-derived scoping, error mapping, and the real `resolutionsApi`
replacing the mock. Exit: `/resolutions` renders from Postgres with the mock deleted.

**CP-C — Remaining read endpoints.** The other five mechanical modules, following the
pattern CP-B establishes.

**CP-D — Writes and concurrency.** Every mutating function is version-guarded; HTTP
needs a contract for that. A stale `expected_version` must surface as a 409 the UI can
act on, not a 500. Exit: a concurrent-edit test drives a real 409 through the browser
layer.

**CP-E — The four orphans.** Whatever §3's open questions resolve to.

**CP-F — States, rate limits, observability.** The exit criterion about the UI
distinguishing draft/approved/**withheld**/failed. Withheld is the hard one and the
discipline already exists: `/packs` renders withheld content without leaking a count,
`/memory` discloses a count because its contract provides one.

**CP-G — Accessibility and keyboard smoke checks**, per the exit criteria.

**CP-H — P3 exit gate.** Acceptance record, as CP10 was for P2.

## 5. Open questions — answer before CP-A starts

1. **What authenticates a user?** There is no credential store. Options: local
   password auth (needs a credentials table, hashing, reset flow — all new surface);
   OIDC against an external provider (no secrets held, but a dependency and config);
   or magic-link email (no passwords, needs mail). This is an owner decision with
   long consequences and it blocks everything.

2. **Session transport: cookie or bearer token?** The frontend is Next.js on the same
   origin, which makes an httpOnly cookie the simpler and safer default. A bearer
   token is friendlier to non-browser clients that do not exist yet. Recommend cookie
   unless there is a known non-browser consumer.

3. **Does the API mirror the 56 domain functions 1:1, or expose task-shaped
   endpoints?** 1:1 is mechanical and reviewable but leaks the domain model into the
   wire format and makes every future refactor a breaking API change.

4. **What happens to `insights.ts`?** See §3. Recommend deciding tile by tile: derive
   or delete, never approximate.

5. **Is `/memory` live or a demo artifact?** It currently renders a baked layout from
   a generated file. Making it live means running graph queries per request against
   Neo4j through the frozen gateway — a real performance and scoping question, not a
   wiring task.

---

## 6. Not in P3 — deliberately

- **Document intake and upload** — P4.
- **Notification delivery** — P8, where CP9 was deferred to (issue #62).
- **External task adapters** — P8. CP7's delivery columns stay inert.
- **Any change to the frozen five.** `retrieve.py` in particular is reached *through*
  its public API; the RBAC gate is not modified to suit an endpoint.

---

## 7. What must not regress

P3 is the first phase where untrusted input reaches this system. The gates that have
held all through P2 hold here too:

- Mechanism gate byte-identical — it has been across CP6, CP7, CP8 and CP10.
- Full gated suite green against real Postgres.
- The five frozen files untouched.
- Every new tenant-scoped relationship uses a composite `(id, workspace_id)` FK.
- No surface states a number it cannot trace to a source.
