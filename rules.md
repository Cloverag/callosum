# Meridian / Callosum — Working Rules

The rules of the road for anyone (human or agent) working in this repo. Authoritative detail lives in the linked docs; this page is the short, enforceable summary. When a rule here and a linked doc disagree, the linked doc wins.

Related: [PRD.md](./PRD.md) · [ROADMAP.md](./ROADMAP.md) · [AGENTS.md](./AGENTS.md) · [CONTRIBUTING.md](./CONTRIBUTING.md) · [docs/architecture.md](./docs/architecture.md) · [docs/ARCHITECTURE_DECISIONS.md](./docs/ARCHITECTURE_DECISIONS.md) · [frontend/DESIGN.md](./frontend/DESIGN.md) · [frontend/PRODUCT.md](./frontend/PRODUCT.md)

## 1. The frozen core is sacred

- The verified retrieval/extraction core (ingest, extract, retrieve, store, schema) is **frozen** at tag `eval-baseline-v3`. Do not edit it to add product features.
- The only sanctioned exceptions are tenancy predicates that *remove* rows (never add), applied brick-by-brick with a failing test first. See [CONTRIBUTING.md](./CONTRIBUTING.md) for the frozen-file list.
- Every change is verified against the frozen eval baseline (mechanism gate: candidate recall, gold-seeded 2-hop traversal, RBAC) before it ships.

## 2. Provenance and permission are non-negotiable

- No AI output mutates institutional memory until an authorized human approves it.
- Every surfaced graph fact carries a machine-checked verbatim source quote. Never show a summary without its evidence.
- Access control excludes confidential content **before** retrieval. Withheld sources are disclosed as a count only — never their content, title, or existence beyond that count.
- **Amendment, owner's decision 2026-08-24 — the count rule has a scope, and the bullet above lost it.** Read literally, the sentence above governs every list in the product. It was written for **retrieval**: `src/callosum/retrieve.py:277` runs the same search twice, once filtered and once not, for the sole purpose of learning the withheld count, and the prompt at `retrieve.py:501` tells the model to say the answer may be incomplete. That cost is paid because an *answer* claims to be complete, and a founder acting on "three sources say X" is harmed by not knowing two more were withheld. A browse list claims nothing of the kind. **The rule as amended:** a clearance-filtered collection discloses a count when a reader would otherwise mistake a partial view for a complete one, and erases when the collection makes no completeness claim — see [ADR-018](docs/ARCHITECTURE_DECISIONS.md), which carries the per-surface table and the reasoning. **Why this is an amendment and not a clarification:** the product already contained both readings, defended in opposing docstrings — `meridian/documents.py`'s `version_chain` discloses a count, `meridian/packs.py` argues that a count is "the same disclosure as returning a placeholder, just quieter" — and one of them had to be wrong under a bullet phrased this way. Neither author was careless; there was no rule to apply. **What does not change:** the prohibition is untouched and absolute — a withheld item never yields its content, title, id, date or position, on either discipline, and "disclosed as a count" remains a ceiling and not a licence to add anything else. Erasure is still the default a new surface gets for free; the count is the deliberate exception, and ADR-018's table is where a new surface earns one.

## 3. Multi-tenancy is fail-closed

- Postgres: RLS `ENABLE` + `FORCE`; runtime connects as the non-superuser `callosum_app` role and sets `app.workspace_id`.
- Neo4j (no RLS): `workspace_id` is baked into entity MERGE identity and every read is scoped. All new/modified Neo4j access goes through the query gateway (`src/callosum/graph.py`); raw `session()` outside the gateway/allowlist is banned by test.
- **Decision, owner's 2026-08-13 — a new Neo4j operation belongs in the gateway, never in `store.py`.** Recorded because two documents pointed at different files and PR #128 was the first work to land on the seam. Left unrecorded, a seam like this gets decided by whichever implementation merges first, which is how an architecture acquires rules nobody chose. [AGENTS.md](./AGENTS.md)'s change rules say to keep "storage operations behind `store.py`" — which reads naturally as covering a Neo4j write — while the bullet above and `src/callosum/graph.py`'s own charter say every new session goes through the gateway. **The gateway wins, and the reason is the frozen boundary, not a preference between two module names:** `store.py` is one of the five frozen modules ([CONTRIBUTING.md](./CONTRIBUTING.md)), where a change requires a *measured* shortcoming against the evaluation baseline, and `graph.py` is not frozen. Routing a new product write through `store.py` therefore converts a product feature into a frozen-core edit and buys nothing for it. AGENTS.md already resolves the same way where it says product layers are built *over* existing functions and do not join the frozen core without measurement; its storage bullet is amended under this date to say so about Neo4j explicitly, so the two documents no longer have to be read together in the right order to agree. **What this does not change:** the `FROZEN_ALLOWLIST` in `tests/test_no_raw_cypher.py` still only shrinks. Its entries are pre-existing sites grandfathered pending migration into the gateway — not a queue new work may join — and [phase.md](./phase.md) carries that retirement as deferred work riding the next planned retrieval change. **What it costs, stated plainly:** the gateway is a bounded repository, one method per query shape with no raw-Cypher entry point, so a new operation means a new named method taking a `GraphContext`. That is more ceremony than adding a function to `store.py`, and it is the price of tenant scoping being impossible to omit rather than merely customary — which is the defect class (D-001) the gateway exists to close.

## 4. How we ship (incremental + measured)

- **Feature work was frozen (2026-08-01),** with two recorded exceptions below. **Superseded 2026-08-13 for the backend — see the amendment below.** Kept here as the record of what was decided, not as a live rule. The target is a portfolio-ready artifact by November. Only critical bug fixes, documentation, demo polish, deployment and evaluation reporting change. Deferred checkpoints (CP-F/G/H, #93) are **not** to be reopened because time remains — reopening them undoes the only thing that makes a deferral honest.
- **Exception, owner's decision 2026-08-04 — meeting preparation. `/prepare` is NEW FEATURE WORK introduced after the P3 freeze.** It is not a bug fix, documentation, demo polish or deployment, so the permitted list above does not cover it; what legitimises it is *authorisation*, recorded here. Classified precisely so nobody later reads it as having always been in scope: it is **consistent with the PRD** (`PRD.md:51` — "board work spans meeting preparation, live discussion, and follow-up"), it is **built on already-shipped backend capability** (P2's `packs` and `agenda` endpoints — no migration, no domain module, no checkpoint), but it was **never assigned to a committed ROADMAP checkpoint**, and `ROADMAP.md`'s operating rule is explicit that nothing is committed until a checkpoint owns it. Devguru's prototype is a pre-intern mockup, not a product contract. **Do not restate this as part of P3.** The flow against the prototype at `devguru-codes.github.io/meridian_pre_intern_work`. It needs **no migration and no new domain module**: `packs` and `agenda` already expose create, reorder, publish and supersede from P2, and the flow is a frontend workflow over endpoints that already shipped. Recorded here rather than smuggled in as polish. **Extended 2026-08-04 to one write:** a suggestion may be added to the agenda, via `POST /api/agenda` — an endpoint that shipped in P2 and had no client. The write creates an ordinary agenda item and nothing else; it does not add a domain concept, a column or a status. Its `description` records why the item was suggested, so the provenance of an agenda item survives outside the page that proposed it. **Two constraints hold inside it:** every suggestion is *derived from a real row and names it* — the agenda comes from open commitments and proposed decisions, never from a language model, because a generated agenda has no source and §2 forbids surfacing anything without one. And readiness reports **counts, not percentages**: the prototype's 90% / 55% / 40% have no denominators, and a percentage implies a measurement that was never taken. The prototype's Finance, HR, Product and CRM sources do not exist in this product and are not to be rendered.
- **Exception, owner's decision 2026-08-09 — the frontend primitive layer.** Re-platforming the UI primitives onto [Base UI](https://base-ui.com) (via shadcn), rebuilding `frontend/src/components/ui/` on top of them, and refreshing page composition. Classified precisely, because none of it is covered by the permitted list above: it is **not** a bug fix, **not** documentation, **not** demo polish, **not** deployment and **not** evaluation reporting. What legitimises it is *authorisation*, recorded here. It is **frontend-only**, which §5 makes the owner's to change, and it **ships no product capability** — no endpoint, no domain concept, no migration, no column, no checkpoint. A reader should understand it as a substitution beneath the existing screens, not as new scope, and **it is not to be restated as part of P3**, whose exit gate stays exactly as the [freeze record](docs/reviews/2026-08-01-p3-freeze.md) left it. **Four constraints hold inside it:** the colour **doctrine** and the WCAG 2.2 AA floor are **unchanged** — blue stays action, violet stays Institutional Memory, the page stays 95% neutral, and no component gained a raw hex. *(Extended 2026-08-09 at the owner's request: the token **values** were rebuilt in OKLCH. Roles, names and meanings are identical — every component consumes the same token it did before — but three defects were measured in the old values and fixed: the neutrals spanned **16.8° of hue** across two Tailwind families, `surface-alt` sat **ΔL\* 0.52** from `surface` and so was an invisible rung, and `danger-emphasis` **failed AA at 4.41:1** on `surface-sunken` under a doc claiming every pairing was verified. The replacement is generated, not eyeballed: one neutral hue anchor, surfaces on visible L\* steps, and each ink solved for ≥5.5:1 on the darkest surface it can occupy. Worst pairing is now **5.54:1**. A palette is exactly the kind of thing §2 means by a measured claim — "verified to AA" is a measurement, and the old one did not hold.)* *(Extended again 2026-08-09: a **dark theme**, which contradicts the light-only rule §6 previously stated and `DESIGN.md` §1 — both amended under the same date rather than left saying otherwise. It is generated, not inverted: elevation reverses, chroma drops, fills take a dark label, and each ink is solved against `surface-alt`, the worst case on a dark ground. Zero failures, worst pairing 5.14:1. **No component changed** — the theme is the token layer resolving differently, which is the Semantic-Only rule finally being cashed in.)* Public component APIs are **preserved**, because 79 `Card`, 45 `Button` and 27 `Badge` call sites consume them and a redesign that rewrites its own call sites is a churn event, not a substitution. It **keeps `DESIGN.md` §5's rule that registry components install into `vendor/`, never into `ui/`** — the CLI's landing zone is unchanged and `retoken.mjs`'s guard against rewriting `ui/` still holds, because `ui/` remains hand-maintained source that merely consumes Base UI primitives instead of raw DOM. The rule was re-read before the work, not after; had the implementation needed to break it, the rule would have been amended in `DESIGN.md` under this date rather than silently violated. And it introduces **no new figures**: a composition change that renders a number nobody measured is a §2 violation regardless of how it looks. *(The duplicate `id="dialog-title"` in `ui/dialog.tsx` is a genuine accessibility defect — that fix is a critical bug fix and needs no exception.)*
- **Amendment, owner's decision 2026-08-13 — backend feature work reopens.** The freeze above rested on a capacity estimate: that the runway to November would not fit further feature work. Eight backend PRs merged between 2026-08-09 and 2026-08-11. That falsifies the estimate — it does not excuse how they landed, and the two are recorded separately here on purpose. **What changes:** backend feature development is open again under Devguru's ownership (§5), and ROADMAP phase order becomes advisory rather than blocking — a phase may begin before the previous one's exit gate is claimed, provided the accepted-count in `ROADMAP.md` is not advanced by it. The product track stands at 3/13 accepted and only an exit gate moves that number. **What does not change, and was never what the freeze was protecting:** §1 — the frozen core, where a tenancy predicate may still only *remove* rows, applied brick-by-brick with a failing test first and the mechanism gate run *before* the change ships, not after; §2 — evidence, provenance and the append-only audit trail, which no feature may record an event into that did not happen; §5 — the frontend belongs to the maintainer; and review before merge, which "commit and push only when the owner asks" already covered and which self-merging one's own pull request does not satisfy. **Permission to build is not permission to self-approve.** That sentence is the governance change this amendment exists to make: the freeze was never what stopped bad work reaching master — review was, and there wasn't any. Eight pull requests merged between 2026-08-09 and 2026-08-11 carried zero reviews between them, and what rode in included a widening of the fail-closed RBAC gate, a notification dispatcher that recorded deliveries it never made, and three migrations whose revision IDs were too long for Alembic to apply. Reopening feature work without restoring review would reproduce that outcome faster, not prevent it. Recorded here rather than left to lapse: a rule that stops being enforced without being amended is worse than either keeping it or dropping it. **How a deferral is reopened:** #62, #93 and #100 may be reopened. A deferral is reopened by **reopening the issue and meeting the acceptance criteria it recorded** — never by closing it with work that does not address them. #93 was closed by a voting policy engine that is not CP-F, CP-G or CP-H; #100 was closed by a 79-line test file while the live graph endpoint, the server-side withheld-count contract and the layout strategy all remain undone. Both now read as resolved while their criteria are unmet. That is the failure the original sentence was guarding against, and it survives this amendment intact.
- **One verified change per commit.** Smallest change that increases confidence. No drive-by refactors, no churn.
- Branch off the default branch; never commit straight to it. **Commit and push only when the owner asks.**
- Fix only real, reproduced bugs. Measure before refactoring — let the problem pick the work.
- Release cadence = merge → freeze → tag → graphify snapshot → publish notes → postmortem. A release is an immutable, self-contained bundle.

## 6. Frontend design rules

Full system in [frontend/DESIGN.md](./frontend/DESIGN.md). The short version:

- **Semantic tokens only.** Components reference roles (`accent`, `surface-raised`, `muted-foreground`, `memory-emphasis`) — never a raw hex or a palette step (`blue-600`, `slate-100`).
- **A token that does not reach the page is not a token** *(added 2026-08-13, from a defect)*. Eighteen utilities across ten files referenced tokens as `rounded-[--radius-card]` — the Tailwind **v3** spelling, which v4 does not wrap in `var()`. The compiled stylesheet therefore contained `border-radius: --radius-card`, an invalid declaration the browser discards in silence: every focal surface rendered with **square corners** against a design document specifying 16px, and six hover transitions fell back to the default duration. Nothing errored and every test was green. The correct spelling is `rounded-(--radius-card)`, and `frontend/__tests__/tailwind-var-syntax.test.ts` now holds it. The general rule this is an instance of: a design system is only as real as its compiled output, so **the claim "the component consumes the token" is itself a measured claim** and is checked like one.
- **Color communicates meaning (95% neutral / 5% semantic):** Blue = action · Green = success · Amber = pending/attention · Red = critical · **Violet = Institutional Memory only** (never a button or nav). No neon, no glow-as-default.
- **Gradients, owner's decision 2026-08-13 — permitted, registered, and measured.** The previous rule read "no gradients"; it is amended rather than dropped, because the dashboard it produced was uniformly flat and the fix the owner chose is a focal surface with depth. **Two constraints make this a design decision instead of a licence.** First, a gradient is **anchored to a semantic family, not free**: the operational hero ramps ink→blue-ink because it carries the primary action, the institutional-memory panel ramps ink→violet-ink. The colour vocabulary that §6 exists to protect is unchanged — violet still never means "button". Second, **at most two gradient surfaces per page**, both deep-ink based, and never on buttons, badges, chips, charts, icons, small panels or text. A third gradient is not a stylistic excess; it is the point at which the page stops having a focal surface at all. **The AA floor is not relaxed — it is sampled differently.** Text on a gradient sits on a *range*, so contrast is verified at the ramp's **lightest point in light theme and its darkest in dark**, never its midpoint, which always flatters a gradient. *(Refined 2026-08-13: the 7:1 gate governs the solid `--focal-foreground`. The **alpha tints** components actually use for metadata — `/70`, `/75` — measure **5.63:1 to 6.96:1**: over the AA floor everywhere, under 7:1. They are scoped to secondary and metadata text accordingly. The original claim was true of the token and had been generalised to every use of it.)* Every gradient in `globals.css` must be declared in `frontend/__tests__/palette-contrast.test.ts` stating whether text sits on it; an undeclared one fails the suite. That test is what makes this amendment enforceable rather than aspirational, and it did not exist before this date — the palette's published figures had been generated, documented and then left unguarded.
- **Motion, owner's decision 2026-08-13 — one scale, four tiers, enforced.** The previous rule was a single line requiring a `prefers-reduced-motion` alternative; motion was otherwise unowned, and what that produced is recorded here rather than glossed. `DESIGN.md` published a hierarchy of **two durations and one ease**. The code shipped **five durations** (120 / 150 / 200 / 350 / 1100ms) and **two rival ease curves**, with `session-gate.tsx` carrying a comment claiming its `[0.22, 1, 0.36, 1]` "mirrors `--ease-out-quart`" — a token whose value is `cubic-bezier(0.16, 1, 0.3, 1)`. Nobody decided to have two curves; they accumulated, one component at a time, under a document that said otherwise. This is the same defect §2 names in a palette — a measured claim left unguarded — and the same remedy applies. **What the rule now is:** motion is a **token layer like colour**. `globals.css` declares one ease and four duration tiers — **L1 hover 120ms · L2 state 200ms · L4 entrance 400ms · L5 reveal 1100ms** — and a component picks a *tier*, never a number. `src/lib/motion.ts` mirrors them for Framer Motion, which animates inline styles from JS and cannot read a custom property. **Four constraints hold inside it.** A **new tier is an amendment, not a call site**: it is declared in `globals.css`, mirrored in `lib/motion.ts` and recorded in `DESIGN.md` under a date, in the one commit. **Nothing loops** — a reveal earns one pass, and an infinite animation is the one kind reduced motion's duration collapse makes *worse*, by turning a slow pulse into a strobe. **Every keyframe sequence ends at the element's natural state**, which is what lets reduced motion switch an animation off outright and land on a correct render rather than collapse its duration into a flash. And **`prefers-reduced-motion` is answered per technology**: the global CSS rule does not reach Framer, whose animations run in JS and never consult a media query, so every Framer call site branches itself — `entity-conflicts/page.tsx` branched its transforms and then animated for a full 350ms anyway, and animated a layout reflow for readers who had asked for none. `frontend/__tests__/motion-contract.test.ts` asserts all of it, including that no component writes a duration or an ease of its own. That test is what makes this amendment enforceable rather than aspirational, and it did not exist before this date.
- **Elevation, not color, reduces flatness.** Four levels: (1) normal white cards — subtle border + tiny shadow; (2) important cards (Meeting Hero, AI panel) — stronger elevation; (3) floating UI (dialogs, dropdowns, command palette) — blur; (4) **the focal surface, owner's decision 2026-08-13** — one deep-ink card per page, permitted to carry a gradient per the rule above, holding the single most important thing on the screen. Level 4 is a *count*, not a style: two of them is none of them. Blur/transparency is reserved for the header, AI sidebar, and floating UI; content cards stay solid for readability.
- **Light-first, with a dark theme as of 2026-08-09.** Light is the tuned palette and the one reviews judge; dark is generated the same way, not inverted, and held to the same AA floor. It is delivered by re-pointing semantic tokens only — a component that needs a `dark:` class to look right is a component that named a colour it should not have. Cards 16px radius, controls 12px, badges fully rounded.
- **WCAG 2.2 AA is a hard floor.** Body text ≥4.5:1 (large ≥3:1), visible non-color-only focus rings, full keyboard paths, `prefers-reduced-motion` alternatives.
- Voice is plain and calm — no sci-fi theatrics.
